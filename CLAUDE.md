# Littoral — notes for working on it

A Seaside-style web framework for SBCL. See README.md for the user-facing tour.

- Toolchain: SBCL only, ocicl for dependencies (`ocicl install <system>` updates `ocicl.csv`), FiveAM for tests. No Quicklisp. Use `sb-thread`/`sb-ext` directly.
- `make test` runs `(asdf:test-system :littoral)` and must stay green. `make e2e NODE=…` checks `littoral.js` in headless Chrome (`tests/e2e/browser.mjs`). In this shell `node` is an nvm stub, so pass `NODE=~/.nvm/versions/node/v24.3.0/bin/node`.
- SBCL servers ignore SIGTERM while Hunchentoot threads run, so stop a test server with `kill -9`.
- Threads do not inherit dynamic bindings: tests that spawn threads must rebind `littoral::*applications*` (see `run-threads` in `tests/robustness.lisp`).
- Tests drive the Lack app in-process through the fake browser in `tests/browser.lisp` (`visit`, `click`, `fill-in`, `press`, `back-to`, `ajax-request`); add tests in that style, not over sockets.
- Packages: `littoral.html` holds the HTML tags and brushes, and `littoral` uses it. Keep generic tag names out of `littoral`'s exports.
- Load order is serial (see `littoral.asd`): util → context → i18n → translations → callbacks → html/{canvas,tags,brushes} → component → decoration → dialogs → backtracking → task → widgets → session → application → configuration → ajax → dispatcher → push → live → tools/{halos,config}.
- Invariants:
  - `decorations` lists are replaced, never mutated, because snapshots store them by value.
  - Rendering must not change state (`*rendering*` makes `show`/`answer`/`home` signal). Tasks are started by `prepare-tasks` after the callbacks run, never during render. Derived data, such as a report's rows, is computed on demand rather than stored at render time.
  - Every URL goes through `url-for` or `page-url`, so the mount prefix and `update-url` apply.
  - AJAX requests reuse the page's continuation and re-snapshot it; they do not create a new `_k`.
  - Static files are served at `static-url`, which carries a content fingerprint (`?v=`). Only a URL with the matching fingerprint is cached as immutable, so browsers never run stale JS.
  - Chrome restores even `no-store` pages from its back/forward cache, so `littoral.js` reloads on `pageshow` when the page was persisted. Browser tests of back-button behaviour must allow for that reload.
  - Woo (optional, `littoral/woo`): its worker threads start with standard I/O syntax (`*print-readably*` true), so every entry point binds `with-sane-printing`. libev is not thread-safe: push on Woo marshals to the stream's event loop with `ev_async_send`; never call a Woo writer from another thread.
- Shared, cross-session state (the wiki and the chat room) lives outside `states`, behind a mutex.
  - Server push: each open page's EventSource is a Clack streaming response (a function). `publish` and `notify` only queue work and wake the stream; rendering happens under the session lock, in whatever serves the stream. On Hunchentoot that's the push hub (`hub-take-over` in `src/push.lisp`): it writes the response head to the socket itself, calls `hunchentoot:detach-socket`, and one thread serves every stream. On Woo it's the stream's event loop (`littoral/woo`). Elsewhere, as in the fake browser, `run-event-stream` waits in the request thread. Tests drive streams in-process (`tests/push.lisp`); `event-streams-hold-no-hunchentoot-thread` (tests/websocket.lisp) checks the hub over real sockets.
  - Presence (`src/presence.lisp`): each stream notes its page's presences, activity and person's name (`note-stream-presences`) when it opens and after each AJAX request (`ajax-json`), under its own session's lock. `presence-viewers` reads only the streams' notes, never another session's components or lock, so two pages showing each other's presence can't deadlock. Register/unregister publish the stream's presences.
- `call` is a `defun/cc`, so it suspends only when called lexically inside `define-flow` (or another `/cc` function).
- `sed` on this machine is GNU sed.
- This machine's ASDF configuration includes `(:tree ~/Projects/common-lisp/)`, so `make test` may load dependencies from other projects' `ocicl/` directories. `make clean-check` (`tools/clean-check.sh`) builds a fresh clone of HEAD against only its own `ocicl.csv`; run it after changing dependencies, and commit first.
- `ocicl lint --fix` is unsafe here: its `needless-shiftf` fix rewrites `(shiftf place '())` to `(setf place nil)`, losing the returned old value, and its `bare-progn-in-if` fix flattens forms onto one line. It also leaves `.bak` files. Fix lint findings by hand. Six findings are deliberate (see the commit that cleaned lint).
- User-visible strings in `src/` go through `translate` (or `translate-plural`), and every one needs entries in `src/translations.lisp` for fr, de and es; the `catalogues-cover-littoral` test fails otherwise. Inside a tag body a `(translate …)` form is written as text, like a literal string. Littoral's exports clash easily with user code (examples define `format-date`), so new exports get distinctive names (`localized-date`, not `format-date`).
- `make new NAME=…` (`littoral/generator`) copies `templates/basic/`, replacing `{{name}}`-style placeholders in file names and contents. The generated project's own suite runs inside ours (`tests/generator.lisp`), so keep the templates' tests passing. Generated packages use `littoral` and `littoral.html`, so templates must not define functions named like their exports (`main` is the HTML tag).
- `littoral/auth`: users come through `*user-store*` (store generics) and are any object with the user generics (`user-id`, `user-name`, …). Never call `db-find 'user` directly; use `find-user-by-id`. Littoral's own tables (`auth_tokens`, `auth_sessions`, `user_roles`, `role_permissions`) key users by `(princ-to-string (user-id user))`. Tests drop them with `drop-auth-tables`, because SQLite reuses ids after a table is dropped. Sign-ins are restored only by `auth-root`'s `initial-request` (never during render). Tests set `*pbkdf2-iterations*` to 1000. Sign-in failures and reset mails are rows in `auth_events`; tests clear them with `littoral.auth::forget-all-events`. `purge-expired-auth-rows` is the nightly cleanup; `note-event` also trims old events at random (1 in 64), so tests age rows with UPDATE after the last failure they record. `register-admin :role` (and `configure-signed-in-admin`) use `signed-in-root` with `restrict-application`; the admin's writes call `check-application-role`.
- Cookies: `set-cookie` queues in the session; `html-response`, `redirect-response` and `handle-ajax` drain the queue, and must never put `:set-cookie` first in the header plist (Clack's Hunchentoot handler fails). The fake browser keeps every Set-Cookie and honours Max-Age=0.
- PostgreSQL: cl-postgres sends NIL as false, so `execute` maps NIL to `:null` there. `LITTORAL_TEST_DATABASE=postgres://…` runs the database suites (`*database-suites*`) against it (`make test-postgres`; CI has a postgres:16 service). Test schemas must work on both (e.g. `SERIAL` vs `INTEGER PRIMARY KEY`; see `postgres-test-p`).
- `littoral/mail` (`src/mail.lisp`, `smtp.lisp`, `outbox.lisp`) builds and sends messages with the `smtp` library (github.com/lispnik/smtp; locally the sibling checkout). It isn't in the ocicl registry: CI, `make clean-check` and the Dockerfiles fetch the tag pinned in `tools/fetch-smtp.sh`, so bump it there. `littoral.mail:smtp-error` is `smtp:smtp-error`; tests make refusals with `smtp:make-reply`. Mail goes through the `mail_outbox` table; each message has a `deliver-mail` durable job (key `mail:ID`), so littoral/mail depends on littoral/jobs and `create-mail-tables` creates the job tables. `start-mail-delivery` sets `*delivery-mailer*` and starts a job runner unless one runs. `smtp-mailer`s pool connections (`:pool-size`) and retry on a dropped one through `smtp:retry-with-fresh-connection`; the tests' fake server serves one connection at a time, so `fake-mailer` passes `:pool-size nil`. Tests call `deliver-queued-mail` (or `run-due-jobs` with only the mail jobs defined, `with-mail-jobs`) rather than waiting for the runner, and the members/mail demos expose `littoral-mail-demo:deliver-now`. A thread's SQLite connection is its own, so tests involving the delivery thread use a file, not `:memory:`. SQLite connections get `*sqlite-busy-timeout*` (5 s) so the thread and requests don't fail on each other's locks. New SQLite connections also switch the file to WAL (`*sqlite-journal-mode*`) and set `synchronous=NORMAL`, once per connection (`prepare-sqlite-connection`); a test spec may give `:journal-mode`, which `connection-arguments` strips before DBI sees it. Files get `-wal` and `-shm` companions, so tests delete those too. CI's real-SMTP test runs against Mailpit with STARTTLS (`LITTORAL_TEST_SMTP`).
- `littoral/jobs` (`src/durable-jobs.lisp`, package `littoral.jobs`) keeps jobs in the `job_queue` table. Core's in-memory `submit-job` already owns names like `job-status` and `cancel-job`, so this package's names say "durable" (`durable-job-status`, `cancel-durable-job`); don't define helpers named like core's job functions in tests. Names and arguments are printed in the package `littoral.jobs.stored`, which uses CL, so `nil` reads back as `nil`. Tests call `run-due-jobs`; runner threads need a SQLite file. Recurring test jobs use their own queue, so other tests' `run-due-jobs` doesn't schedule them. `create-job-tables` records the database (`job-tables-p`), as `create-mail-tables` does for the outbox, like the audit log: /metrics reports those databases (through `add-metrics-source`), and the admin's "Job queue" page (`job-queue-view`, in `src/admin.lisp`) shows only there. The admin tests have a table called "Jobs", hence the page's name.
- Metrics (`src/observe.lisp`): counters and histograms are made with `define-metric` at load time and fed with `count-metric`/`observe-metric`/`timing-metric` (an undefined name signals); values computed at scrape time (database counts, pools, file sizes) are `add-metrics-source` functions, each over the databases its subsystem recorded. Label values must stay few: never users, addresses or job arguments. Tests call `reset-metrics` first and read values with `metric-value` (`tests/observe.lisp`).
- `littoral/audit` (`src/audit.lisp`): `audit` writes only to databases whose `create-audit-tables` ran in this process (`create-auth-tables` and `register-admin` call it), so code that records events works without the table. `drop-auth-tables` drops the log too. littoral/auth sets `*audit-actor*` to the session's user; outside a request the actor is NIL. Event details are a plist stored as JSON.
- Migrations (`src/migrations.lisp`, in `littoral/db`): Littoral's own tables are the SQL files under `migrations/<set>/`, with `.sqlite.sql` and `.postgres.sql` variants; change them by adding a numbered file, never by editing an applied one or going back to `create-table`. The `drop-*-tables` functions call `forget-migrations`, so tests that drop and recreate tables get them back. `define-migrations` signals at load if its directory is missing, so Dockerfiles must copy `migrations/`.
- `make test`'s "Did N checks" undercounts: the generator tests run nested FiveAM suites. Count with `(fiveam:run 'littoral/tests::littoral)` when it matters.
- API examples live in `docs/examples/NN-area.lisp`: `;;;; Example: pkg:symbol …` headers, `;;; ` prose, code, and `;; ⇒ value` lines (what the REPL prints). `tools/doc-examples.lisp` runs each in its own thread and fresh package (using cl, littoral, littoral.html, littoral.test), with fresh application, endpoint and catalogue tables and the registries in `*optional-registries*` isolated; the `doc-examples` suite runs them all, `make examples EXAMPLES=FILE` one file. Examples run inside the suite, so they must leave no global state behind; add any new global registry to `*optional-registries*`. `make docs` copies them under each symbol and lists symbols without one. The tutorial's blocks are checked against `docs/tutorial/*.lisp` and pasted in order by `tutorial-pasted-in-order`. The README's blocks are read by `readme-blocks-read` (tests/readme.lisp), so every `littoral…:name` in them must be exported; complete blocks are run by tests that find them by a line they contain (`readme-block`), so keep those lines unique when editing.
- `docs/API.md` is generated (`make docs`); edit docstrings, not the file. It covers the packages listed in `write-api-docs` (`tools/api-docs.lisp`); sections follow `;; Heading` comments in each package's `:export`. Words in `*acronyms*` stay words; other capitalised words become code. `defun/cc` drops docstrings, so `/cc` functions get theirs with `(setf (documentation …))`.
